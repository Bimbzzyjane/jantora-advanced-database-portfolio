# Task 4: Keys and Constraints

## 4.1 Introduction

In designing the Jantora Superstores database, I used keys and constraints to connect related tables and reduce the chances of storing incorrect information. These rules are defined in `01_schema.sql` and are enforced by PostgreSQL when records are inserted or updated.

## 4.2 Primary keys

A primary key identifies each row in a table. All nine tables have a single-column integer primary key: `category_id`, `branch_id`, `customer_id`, `product_id`, `inventory_id`, `order_id`, `order_item_id`, `payment_id`, and `delivery_id`, respectively. The IDs use `GENERATED BY DEFAULT AS IDENTITY`, which generates a value when none is supplied. The `PRIMARY KEY` constraint, rather than the identity generator alone, ensures that the ID is unique and not null.

## 4.3 Foreign keys

Foreign keys maintain relationships between tables. The following foreign keys appear in the implemented schema:

| Child table and column | References | Why it is needed |
|---|---|---|
| `products.category_id` | `categories.category_id` | Each product belongs to an existing category. |
| `inventory.branch_id` | `branches.branch_id` | Each stock record belongs to an existing branch. |
| `inventory.product_id` | `products.product_id` | Each stock record refers to an existing product. |
| `orders.customer_id` | `customers.customer_id` | An order can be linked to a customer; this field is optional for walk-in purchases. |
| `orders.branch_id` | `branches.branch_id` | Each order is assigned to a branch. |
| `order_items.order_id` | `orders.order_id` | Each order item belongs to an existing order. |
| `order_items.product_id` | `products.product_id` | Each order item refers to an existing product. |
| `payments.order_id` | `orders.order_id` | Each payment record is associated with an order. |
| `deliveries.order_id` | `orders.order_id` | Each delivery record is associated with an order. |

PostgreSQL rejects a non-null foreign-key value that does not match a referenced record. For example, an order item cannot refer to a product ID that does not exist.

## 4.4 Other constraints

| Constraint | Example in Jantora | Purpose |
|---|---|---|
| `NOT NULL` | `products.product_name`, `orders.branch_id` | Requires a value for essential fields. |
| `UNIQUE` | `customers.email`, `branches.branch_name` | Prevents duplicate values in these columns. |
| Composite `UNIQUE` | `inventory(branch_id, product_id)` | Prevents two stock records for the same product at the same branch. |
| Composite `UNIQUE` | `products(category_id, product_name)` | Prevents repeating the same product name within a category. |
| Composite `UNIQUE` | `order_items(order_id, product_id)` | Prevents duplicate lines for the same product in one order. |
| `UNIQUE` on a foreign key | `payments.order_id`, `deliveries.order_id` | Limits the current design to at most one payment and one delivery record per order. |
| `CHECK` | `products.price >= 0` | Rejects negative product prices. |
| `CHECK` | `inventory.quantity >= 0` | Rejects negative stock quantities. |
| `CHECK` | `order_items.quantity > 0` | Requires at least one unit on an order line. |
| `CHECK` | `orders.order_type IN ('ONLINE','IN_STORE')` | Restricts order types to the two supported values. |
| `DEFAULT` | `inventory.quantity DEFAULT 0` | Supplies an initial value if the column is omitted. |
| `DEFAULT` | `orders.ordered_at DEFAULT CURRENT_TIMESTAMP` | Records the order time when not supplied. |

The schema also restricts order, payment, and delivery statuses to predefined values. A further check on `orders` requires a customer ID when `order_type = 'ONLINE'`, while permitting a null customer ID for an in-store purchase. In `deliveries`, the date checks require a dispatch timestamp before a delivery timestamp and prevent delivery time from being earlier than dispatch time.

## 4.5 How these rules support the business

For Jantora Superstores, the constraints help prevent common mistakes. The inventory rule avoids negative recorded stock, and the combination of branch ID and product ID ensures that stock is recorded separately for each branch. The online-order check helps us link online purchases to registered customers. Foreign keys prevent records from referring to missing branches, products, or orders.

## 4.6 Current design limitations

These constraints protect individual records but do not solve every business rule. For example, `quantity >= 0` does not automatically deduct stock after an order or stop two concurrent transactions from selling the same stock. We will examine transaction handling in Portfolio 3. Also, the one-payment-per-order and one-delivery-per-order rules simplify this assessment but would need reconsideration if Jantora later supports split payments, payment retries as separate records, or multiple shipments per order. The current delivery table stores the latest status, not a complete tracking history.
